# V0.2.5 交互与回执 / Navigation and delivery receipts

## 中文

本次规则取代 V0.2.4 必须顺序翻完详情的规则。长内容仍完整保留，不调用模型精简；允许主动跳过阅读，但不默认选择批准。跳到末尾后仍需要选择、短按确认、释放按键，再长按确认 1 秒提交。

| 当前界面 | 短按上 / 下 | 长按上 / 下 | 短按确认 | 长按确认 |
| --- | --- | --- | --- | --- |
| 请求详情 | 上 / 下一页 | 跳到首张详情 / 最后决策页 | 静音 | 显示转到 Mac 处理指引并静音 |
| 最后决策页 | 选择允许 / 拒绝 | 返回首张详情 / 留在末页并清除选择 | 进入二次确认 | 显示转到 Mac 处理指引并静音 |
| 二次确认 | 上取消选择，下静音 | 取消当前选择，回到首张详情 / 最后决策页 | 不提交 | 释放后重新长按 1 秒提交当前选择 |
| 转到 Mac 的指引页 | 不提交操作 | 回到首张详情 / 最后决策页 | 返回设备审阅 | 保持指引，不提交 |

请求已提交、等待回执时，不允许方向键或重复确认再次提交。请求 ID、摘要、Bridge epoch、设备 boot、连接状态和期限检查保持有效。新固件显式声明 `review_jumps: true`；旧固件仍按其原有顺序翻阅规则处理。即使直接跳末页，也必须等该页实际送达后才开放决策。

“转到 Mac”是设备上的交接指引。App 原有的审批窗口继续保留；它不会自动点击、批准或打开另一个聊天。设备明确显示“尚未提交允许或拒绝”，短按确认可以回到设备继续审阅。等待用户回复的问题依旧只能在 Mac 上回答。

此前的 `approval_sent` 可能一直等待只由部分 PostToolUse 结果提供的反馈。新版 App relay 只有在赢得 Mac/设备单次作答仲裁，并将准确的原生审批结果写入且 flush 到真实 App 后端后，才发出绑定请求的提交回执。允许的回执显示 😆 三秒及“批准已送达 Codex”，随后恢复实际工作/待机状态。该表情表示批准已提交，不表示任务执行成功。匹配的实际拒绝/部分授权结果有优先权；重复、过期、错请求或旧 boot 回执不重放表情。10 秒未取得提交回执则提示“回执未确认 · 请在 Mac 查看”，不会伪造授权成功。

官方 `serverRequest/resolved` 可以表示已作答，也可以表示请求被清除，不能单独作为授权成功证据。参考：[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)。

### 更新与验收

1. 只在旧 Bridge 终端按 Control+C，连接 USB 数据线。
2. 运行 `更新交互与回执固件.command`。脚本先核对 App 版本，双读 8 MB 备份，只写 factory 应用并回读验证；不重新配网，不改账户、NVS、分区表或 bootloader。
3. 刷机后按脚本提示手动 Command+Q 退出 App，再回终端按回车启动 App 与 Bridge。从侧栏重新打开原聊天；聊天不会被删除。此步骤用于加载新的 relay 回执代码，单独重启 Bridge 不够。

主机验证：140 页请求首/末跳转、二次确认页两个方向的长按返回、释放不补触发、详情/确认页长按确认不同含义、绑定和加载完成检查，以及实际 stdio + Unix IPC 的允许/拒绝回执、Mac 抢先作答、超时和真实拒绝优先。使用实际 LVGL 字库渲染了五种屏幕；没有缺字。固件 0.2.5 已刷入并回读校验，Wi-Fi 在线。2026-10-25，原 App 的真实网络申请由设备选择允许，Bridge 的设备选择与 relay 提交回执 ID 匹配，官方工具返回本轮网络权限已授予。用户确认设备正确显示 😆。

## English

V0.2.5 replaces mandatory sequential review with explicit endpoint jumps. All request details remain available without model summarization. Hold Up goes to the first detail page; hold Down goes to the final decision page. Short Up/Down browse details or select Allow/Deny on that final page. No choice is preselected.

Short OK on a selected decision opens the second confirmation. A fresh one-second OK hold submits it. From that confirmation, holding either direction cancels the choice and returns to the first detail/final decision page respectively, even when the page number is unchanged. Releasing a held key never generates a short press.

Holding OK while browsing or choosing a decision shows a Mac handoff screen and mutes reminders. It explicitly states that no Allow/Deny was submitted; short OK returns to hardware review. The native App approval remains available on Mac. No UI clicking, automatic grant, or chat switching is performed. Holding OK inside the second confirmation exclusively submits its selected decision.

The relay emits a bound delivery receipt only after winning single-response arbitration and flushing the exact approval reply to the real App backend. Allow displays 😆 and “Approval delivered to Codex” for three seconds before resuming actual state. This acknowledges submission, not successful task execution. A matching actual denial/partial grant takes precedence. Missing receipts time out after ten seconds with an explicit unconfirmed status; stale/replayed receipts cannot manufacture success. The official `serverRequest/resolved` event alone is insufficient evidence because it also covers cleared requests: [App Server documentation](https://learn.chatgpt.com/docs/app-server).

To update, stop only the old Bridge terminal with Control+C, connect USB, and run `更新交互与回执固件.command`. The updater verifies two full backups and writes/verifies only the factory application, retaining pairing and other flash regions. After flashing it asks you to manually quit the App, then press Return to relaunch the App and Bridge. Reopen the original chat from the sidebar. Relaunching the App is necessary to load the new relay code; restarting only the Bridge is insufficient.

Controller tests, 140-page endpoint regressions, real stdio/Unix IPC Allow/Deny receipts and Mac-side arbitration, timeout/denial precedence, and five actual-font LVGL previews are checked. Firmware 0.2.5 is flashed and readback-verified, and Wi-Fi is online. On 2026-10-25, a real network request in the original App was allowed on the device; physical-decision and relay-delivery IDs match, and the official tool returned a turn-scoped network grant. The user confirmed the 😆 feedback displayed correctly.
